JavaServer Faces

JSF is a component lifecycle: decode, validate, update the model, invoke the action, then render.

~50 minState machine3 objectives5 subgoals
  • List the JSF request lifecycle phases in order.
  • Explain where conversion and validation run relative to the model update.
  • Describe the role of a managed bean in a JSF page.

LessonSubgoals

Read the subgoals first. Each one is a small, checkable idea that the worked example and the playground will use.

  1. The view is a component tree

    A Facelets page becomes a tree of components. The lifecycle walks that tree; it is not a simple template render.

  2. Decode maps input to components

    Submitted values are applied to component local values. The model is not touched yet.

  3. Validation can short-circuit

    If a converter or validator fails, the lifecycle jumps to render response. The action never runs with invalid data.

  4. Update model copies to the bean

    Only after validation do component values move into the managed bean. This ordering protects the model.

  5. Invoke, then render

    The action method runs after the model is valid. The response may be a forward to another view or the same view with messages.

Worked exampleRegistrationBean: one form, one lifecycle

The bean holds the model. The page binds inputs to properties. The button invokes an action only after validation succeeds.

<h:form>
  <h:inputText value="#{registration.name}" required="true" />
  <h:inputText value="#{registration.email}" required="true" />
  <h:commandButton value="Register" action="#{registration.submit}" />
</h:form>

@ManagedBean
public class RegistrationBean {
    private String name;
    private String email;
    public String submit() { return "confirmed"; }
}

  1. Build the view

    The form and its inputs become component objects. The value expressions are stored on the components.

  2. Apply request values

    The submitted strings are stored as local values on each input component.

  3. Process validations

    required fails on an empty field. A failure sends the lifecycle directly to render response.

  4. Update model

    Valid values are written through the expressions into the managed bean properties.

  5. Invoke application

    submit runs with a valid bean. Its return value selects the next view.

Predict, then observe

Before you step: If the email field is empty, does RegistrationBean.submit run?

No. The required validator fails during process validations, so the lifecycle skips update model and invoke application and re-renders with an error message.
