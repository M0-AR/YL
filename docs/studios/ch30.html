Multithreading and Parallel Programming

Threads make progress concurrent; synchronization makes shared state predictable. You need both, and they solve different problems.

~55 minState machine3 objectives5 subgoals
  • Identify a race condition in interleaved reads and writes.
  • Use synchronization or an atomic type to protect shared state.
  • Explain why starting a thread and joining it are different events.

LessonSubgoals

Read the subgoals first. Each one is a small, checkable idea that the worked example and the playground will use.

  1. Interleaving is not sequential

    Two threads can read the same old value before either writes. The final state can be as if one update never happened.

  2. count++ is three steps

    Read, add, write. A thread can be paused between any two. The increment is not atomic just because it is one line.

  3. Synchronization defines a critical section

    A lock ensures one thread at a time executes the protected block. The lock must be the same object for every access.

  4. Atomics compose a single operation

    AtomicInteger.incrementAndGet is one atomic operation. It helps for counters, not for invariants spanning several fields.

  5. Join establishes happens-before

    join waits for a thread to finish and makes its writes visible to the joining thread. Without it, the main thread may read before the work is done.

Worked exampleLostUpdate: two threads, one increment each

The final value is 1, not 2. Both threads read the same zero before either wrote.

int count = 0;
Thread a = new Thread(() -> count++);
Thread b = new Thread(() -> count++);
a.start();
b.start();
a.join(); b.join();

  1. Initial state

    count is 0. No thread has started.

  2. Start both

    The scheduler may run either thread first. Start order does not guarantee execution order.

  3. A reads 0

    A has read the old value but has not written yet.

  4. B reads 0

    B also reads 0 before A writes. The race window is open.

  5. Both write 1

    A writes 1, then B writes 1. One increment is lost. Join waits for both, but it cannot repair the race.

Predict, then observe

Before you step: Does making the field volatile fix the lost update?

No. Volatile ensures visibility of reads and writes, but count++ is still three separate steps. Use a lock or AtomicInteger.

PracticeRebuild the program

A Parsons problem: the lines are correct, but the order is not. Rearrange them until the program would compile and behave as described.
