Web Services

A web service is a contract over HTTP: method, path, representation, status, and the rules for repeating a request.

~50 minState machine3 objectives5 subgoals
  • Map CRUD operations onto HTTP methods and status codes.
  • Explain idempotency and why retries are safe for some methods.
  • Separate transport concerns from representation and resource state.

LessonSubgoals

Read the subgoals first. Each one is a small, checkable idea that the worked example and the playground will use.

  1. Resources have identifiers

    A URI names a resource. /books/42 is a resource; the JSON is one representation of it.

  2. Methods carry intent

    GET reads, POST creates, PUT replaces, PATCH partially updates, DELETE removes. The method is part of the contract, not decoration.

  3. Status codes are part of the response

    200 means success, 201 means created, 400 means a bad request, 404 means missing, 409 means a conflict, 500 means server failure.

  4. Idempotency makes retries safe

    Repeating a GET, PUT, or DELETE should have the same effect as one call. POST is not generally idempotent.

  5. Representations are negotiated

    Content-Type describes the body; Accept requests a representation. JSON is common but not the only option.

Worked exampleBookEndpoint: read one resource

The path identifies the resource, the method states the intent, and the status reports the outcome.

GET /api/books/42
Accept: application/json

200 OK
Content-Type: application/json
{"id":42,"title":"Distributed Systems","year":2020}

  1. Request line

    GET is safe and idempotent: it should not change server state.

  2. Representation request

    Accept tells the server the client prefers JSON. The server may return another supported type.

  3. Lookup

    The server maps the path to a resource identifier and queries its store.

  4. Success status

    200 means the representation is in the body. A missing book would be 404, not an empty 200.

  5. Body

    The JSON is a representation, not the resource itself. Another request could ask for XML or a summary.

Predict, then observe

Before you step: A client retries the same GET after a timeout. Is that safe?

Yes. GET is safe and idempotent, so repeating it should not change state. The retry may return a newer representation, but it will not create a duplicate.
