Event-Driven Programming and Animations

A GUI program does not run top to bottom; it waits for events, then runs the handlers you registered.

~45 minState machine3 objectives5 subgoals
  • Trace an event from its source through a registered handler to a visible state change.
  • Write a lambda handler that updates model state instead of only changing a label.
  • Explain why animation state belongs on the application thread.

LessonSubgoals

Read the subgoals first. Each one is a small, checkable idea that the worked example and the playground will use.

  1. The source raises, the handler responds

    A button is an event source. setOnAction stores a handler. When the button fires, the toolkit calls that handler with an event object.

  2. Registration is not execution

    The line that registers a handler runs once. The handler body runs later, once per event. Reading code in order can hide that gap.

  3. State first, pixels second

    Update an int or model object, then refresh the label from that state. If the label is the only state, every new feature has to reverse-engineer it.

  4. Animation is timed state

    A Timeline or AnimationTimer updates a property on each pulse. The same state-change rule applies, just many times per second.

  5. One thread owns the scene

    Handlers and animation callbacks run on the JavaFX application thread. Blocking that thread freezes input, animation, and rendering together.

Worked exampleClickMeter: one counter, two observers

The handler changes the counter. The label is refreshed from that counter, so the button text and the status line can never disagree.

public class ClickMeter extends Application {
    private int clicks = 0;
    private final Label output = new Label("Clicks: 0");
    @Override
    public void start(Stage stage) {
        Button add = new Button("Add one");
        add.setOnAction(event -> {
            clicks++;
            output.setText("Clicks: " + clicks);
        });
        VBox root = new VBox(8, add, output);
        stage.setScene(new Scene(root, 240, 120));
        stage.show();
    }
}

  1. Initial state

    The field starts at zero and the label starts with the same value. Two representations, one source of truth.

  2. Create the source

    The button exists but has no behavior. Clicking it now would do nothing visible.

  3. Register, do not run

    The lambda is stored. Its body runs only when an action event reaches the button.

  4. Event dispatch

    A click fires the handler on the application thread. The counter changes before the label is touched.

  5. Refresh from state

    The label derives its text from clicks. A reset or undo feature can now update one field and call the same refresh.

Predict, then observe

Before you step: If the handler increments clicks twice but sets the label only once, what does the label show after one click?

It shows the new value, because the single refresh reads the field after both increments. The label reflects state at refresh time, not the number of increments.

PracticeRebuild the program

A Parsons problem: the lines are correct, but the order is not. Rearrange them until the program would compile and behave as described.
