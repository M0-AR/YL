Networking

A socket is a byte stream between two processes; a protocol is the agreement about what those bytes mean.

~50 minState machine3 objectives5 subgoals
  • Distinguish a listening server socket from an accepted connection.
  • Trace a request and response across a TCP connection.
  • Explain why message framing is required on a byte stream.

LessonSubgoals

Read the subgoals first. Each one is a small, checkable idea that the worked example and the playground will use.

  1. Bind, listen, accept

    A ServerSocket binds a port and listens. accept returns a new socket for one client; the listening socket stays open.

  2. Connect performs the handshake

    A client Socket constructor connects to a host and port. When it returns, the transport is ready for bytes.

  3. Streams carry bytes, not messages

    TCP delivers an ordered byte stream. It does not preserve write boundaries, so the receiver must know how to find the end of a message.

  4. Close both directions

    Closing a socket releases the file descriptor. Try-with-resources closes the stream chain and the socket together.

  5. Blocking calls need threads or timeouts

    accept and read block until data or closure arrives. A server that handles one client at a time stalls everyone else.

Worked exampleEchoPair: one line across the wire

The server accepts, reads one line, and writes it back. The client sends and then reads the reply.

ServerSocket server = new ServerSocket(5000);
Socket client = new Socket("localhost", 5000);
Socket accepted = server.accept();
PrintWriter out = new PrintWriter(client.getOutputStream(), true);
out.println("ping");
String reply = new BufferedReader(
    new InputStreamReader(accepted.getInputStream())).readLine();

  1. Listen

    The server socket owns port 5000. No client is connected yet.

  2. Connect

    The client socket completes the TCP handshake. The server's accept call can now return.

  3. Accept

    The accepted socket represents this one connection. The listening socket remains available for others.

  4. Write

    println appends a newline. The newline is the framing that lets readLine know the message ended.

  5. Read

    The server reads until the newline. Without the newline or a length prefix, the read would wait for more bytes.

Predict, then observe

Before you step: What happens if the client writes "ping" without a newline and the server calls readLine?

readLine blocks waiting for a line terminator or end of stream. The bytes arrived, but the message boundary did not.

PracticeRebuild the program

A Parsons problem: the lines are correct, but the order is not. Rearrange them until the program would compile and behave as described.
